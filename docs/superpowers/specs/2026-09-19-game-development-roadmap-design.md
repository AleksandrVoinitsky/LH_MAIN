# Архитектура и дорожная карта разработки игры

## Цель

Определить поэтапную, ориентированную на код разработку «Лакхантеры: Вирус V»: от серверной и сетевой основы до игровых сценариев, мета-игры и эксплуатации. Документация должна быть достаточным контекстом для разработчиков и агентов без обращения к истории обсуждений.

## Границы работ

В область работ входят программный код, сервисы, сетевые протоколы, данные, тесты, контейнеризация, наблюдаемость и технические конфигурации.

В область работ не входят создание и наполнение карт, 3D-моделей, анимаций, звука, VFX, финального UI, художественных материалов и балансировка контента. Код предоставляет для них конфигурации, интерфейсы и точки интеграции.

## Технологические решения

| Область | Решение |
|---|---|
| Unity-клиент и match-server | Unity 6000.3.14f1, C#, FishNet 4.7.3 |
| Авторитетная игровая симуляция | Linux headless Unity dedicated server с FishNet |
| Внешние сервисы | C#, ASP.NET Core в одном `backend-api` на первом этапе |
| Постоянное хранение | PostgreSQL с миграциями |
| Локальная среда | Docker Compose |
| Целевой начальный пул матчей | Два заранее поднятых контейнера Unity game-server |
| Production-оркестрация | Не входит в текущий этап; контракты не должны блокировать последующий переход к отдельному allocator и оркестратору |

## Контейнерная архитектура

```text
Unity client
  | HTTPS / WebSocket
  v
backend-api (ASP.NET Core)
  |-- PostgreSQL
  |-- identity, profiles, progression, matchmaking
  |-- match sessions, server allocation module
  |
  | internal authenticated contract
  +--> game-server-1 (Unity Linux headless + FishNet)
  +--> game-server-2 (Unity Linux headless + FishNet)
```

### Ответственность компонентов

- `backend-api` владеет dev-аккаунтами, безопасным хранением паролей, JWT, профилями, инвентарём, прогрессией, очередью матчмейкинга, метаданными матчей, выдачей match ticket и итоговыми наградами.
- PostgreSQL хранит только постоянные данные и результаты. Тиковое состояние активного матча в ней не хранится.
- Каждый Unity game-server владеет только одним активным матчем и выполняет авторитетную симуляцию: подключения, движение, бой, состояния, лут, ИИ, зона, эвакуация и результат матча.
- Клиент отвечает за ввод и отображение. Он не является авторитетом состояния и не может самостоятельно начислять награды или изменять инвентарь.
- Модуль allocation в `backend-api` выбирает только здоровый свободный заранее запущенный game-server. Доступ к Docker Engine и динамический запуск матчевых контейнеров в текущий этап не входят.

## Идентичность и вход

Первый технический срез использует dev-логин и пароль, которые хранятся в PostgreSQL с безопасным хешированием. Backend выдаёт короткоживущий JWT для API.

Перед соединением с матчем backend выдаёт короткоживущий, одноразовый или защищённый от повторного использования match ticket. Unity game-server проверяет ticket через внутренний контракт backend до допуска игрока в матч.

Email-подтверждение, восстановление пароля, социальный вход и финальный UI авторизации не входят в первую версию.

## Правила сети и производительности

- FishNet является основой для транспорта, репликации, RPC, observer/interest management и dedicated-server сценария.
- Не создавать собственные транспорт, протокол снапшотов, репликацию или оркестратор без документированного измеримого ограничения готового решения.
- Вся критичная игровая логика исполняется на Unity server: валидируются ввод, скорость, позиции, урон, инвентарь, лут, награды и завершение матча.
- Система проектируется на матч до 40 игроков. Ручная отладка допускается на меньшем числе клиентов, но этап сетевого фундамента считается готовым только после воспроизводимого нагрузочного сценария на 40 клиентов-заглушек или headless-клиентов.
- Оптимизации вносятся только после профилирования и измерений. Бюджеты тиков, памяти, сетевых сообщений и времени кадра сервера фиксируются как критерии конкретных этапов, а не предполагаются заранее.

## Последовательность этапов

1. Основа разработки: структура C#-решения, контракты без Unity API, конфигурация, Docker Compose, тесты и CI.
2. Backend и постоянные данные: PostgreSQL, миграции, dev-аккаунты, JWT, профиль, health checks.
3. Unity dedicated server: Linux headless build, FishNet-конфигурация и два заранее запускаемых контейнера.
4. Матчевый контур: очередь, match ticket, резервирование server-slot и подключение клиента к назначенному серверу.
5. Сетевой фундамент матча: до 40 игроков, серверный спаун, движение, observer management и измерение нагрузки.
6. Первый игровой цикл: состояния персонажа, урон, тяжёлое ранение, смерть, эвакуация, сохранение результата и награды.
7. Основной матч: зона, лут, инвентарь, оружие, гранаты, эффекты и серверная валидация действий.
8. Расширение мира: PvE/ИИ, обнаружение, транспорт, точки интереса и программные спаун-системы.
9. Мета-игра: лобби, группы, прогрессия, ресурсы, магазин, ключи и премиальные механики.
10. Режимы и эксплуатация: «Альянс», «Измена», администрирование, метрики, резервное копирование и подготовка к масштабированию.

4. Готовые технологии и обязательные паттерны.

6. Упорядоченный кодовый результат.

`roadmap.md` является точкой входа: агент сначала определяет текущий этап, затем читает его документ и связанные архитектурные правила.

## Вне рамок дорожной карты

- Разработка контентных ассетов и карт.
- Kubernetes, Agones и автоматическое создание Unity-контейнера на каждый матч.
- Самописная замена готовым сетевым возможностям FishNet.
- Полная пользовательская система регистрации и восстановления доступа до завершения технического вертикального среза.
